# LogKeeper: розумна захищена система пріоритетної реплікації журналів подій

Командний семестровий проєкт з дисципліни «Алгоритми і оптимізація програмних рішень» (Проєкт 3).

Система приймає потік подій журналу, оцінює їхню важливість, стискає, вирішує,
у скількох копіях і в якому порядку записати їх на вузли з обмеженим бюджетом,
шифрує репліки та після відмов відновлює журнал, зберігаючи максимум критичних подій.

## Команда

| Учасник | Модуль (зона відповідальності) | Папка |
|---|---|---|
| Максим (керівник проєкту) | Інтеграція та відновлення, спільні типи | `src/LogKeeper.Integration/`, `src/LogKeeper.Core/` |
| Ігор | Планувальник реплікації: ДП + жадібні алгоритми | `src/LogKeeper.Scheduler/` |
| Проскура Даня | Класифікація подій: перцептрон | `src/LogKeeper.Classifier/` |
| Таран Даня | Захист (PBKDF2, AES, HMAC) + генетичний алгоритм + атака | `src/LogKeeper.Security/` |
| Міша | Стиснення: канонічний Гаффман | `src/LogKeeper.Compression/` |

Тести кожного модуля лежать у `tests/LogKeeper.Tests/<Модуль>/`.

## Що робить система

- **Вхід:** потік 16-байтових записів журналу (час, джерело, код події, показник, категорія, severity, critical, прапорець).
- **Обробка:** класифікація → стиснення → вибір кількості копій → порядок реплікації → шифрування.
- **Вихід:** репліки на вузлах A/B/C; після відмов — відновлений журнал і метрика якості Q.

## Архітектура

```
потік подій
 → Classifier   (перцептрон: клас 0/1/2)
 → Compression  (канонічний Гаффман)
 → Scheduler    (ДП: скільки копій; жадібний: на який вузол і в якому порядку)
 → Security     (PBKDF2 → AES-256-CTR → HMAC)
 → вузли        (replication.py, не змінюємо; запускається з C# як зовнішній процес)
 → Integration  (перевірка HMAC → розшифрування → декодування → дедуплікація → відновлення)

Core                           — спільні типи (LogRecord, RecordCodec)
Security/GeneticAlgorithm.cs   — генетичний алгоритм налаштовує параметри
Security/WeakCipherAttack.cs   — модуль атаки для тижня змагань
Integration                    — зв'язує всі модулі, рахує метрику Q
```

Залежності проєктів: `Integration` бачить усі модулі; `Classifier` бачить лише `Core`;
решта модулів не залежать одне від одного.

## Основні алгоритми

- Багатошаровий перцептрон (власна реалізація) — визначає цінність події.
- Канонічний Гаффман — зменшує розмір журналу.
- Динамічне програмування (багатоваріантний рюкзак) — вибір кількості копій 0/1/2/3 в межах бюджету.
- Жадібна евристика — порядок і вузли для реплікації.
- AES-256-CTR + HMAC-SHA256 (Encrypt-then-MAC) — захист реплік.
- Генетичний алгоритм — підбір параметрів системи.

## Запуск програми та експериментів

### Наскрізний запуск

```bash
dotnet run --project src/LogKeeper.App -- --scenario all
```

Шлях даних: події → перцептрон (клас 0/1/2) → Гаффман → ДП (скільки копій) → порядок і вузли →
PBKDF2 + AES-256-CTR + HMAC (пакети LOG3) → вузли A/B/C → відмови за сценарієм →
перевірка HMAC → розшифрування → декодування → дедуплікація → метрики S, R, T, Q.
Займає ~30–60 с (навчання перцептрона і PBKDF2 на 100 000 ітерацій для кожного пакета).

| Аргумент | Значення | За замовчуванням |
|---|---|---|
| `--scenario` | `none`, `node-loss`, `two-node-loss`, `corrupt`, `mixed` або `all` | `mixed` |
| `--input` | власний вхідний файл: `.bin` (16-байтові записи підряд) або `.csv` | `materials/session.bin` → `session.csv` → синтетика |
| `--materials` | папка з матеріалами викладача | `materials/` поруч із `LogKeeper.sln` |
| `--strategy` | `dp` або `greedy` — вибір кількості копій | `dp` |
| `--replication-args` | шаблон аргументів `replication.py`, плейсхолдери `{dir}`, `{scenario}` (D-005) | вузли в пам'яті |

Сценарії відмов: `none` — без відмов; `node-loss` — втрачено вузол A; `two-node-loss` — A і B;
`corrupt` — пошкоджено перший пакет на вузлах B і C; `mixed` — втрачено C і пошкоджено перший пакет A.

Пароль реплік береться зі змінної середовища `LOGKEEPER_PASSWORD` (інакше — демонстраційний).

### Експерименти

```bash
dotnet run --project experiments/LogKeeper.Experiments -c Release -- all
```

або окремо: `dp-vs-greedy`, `classifier`, `ga`, `ablation`, `final`. Таблиці пишуться в `results/`
(`.md` і `.csv`). Повний прогін `all` триває ~10 хв, найдовші — `ga` (~5 хв) і `ablation` (~3.5 хв).
Деталі — [experiments/README.md](experiments/README.md).

> Запуск експериментів перезаписує `results/`. Усі генератори мають фіксовані seed, тож змінюються
> лише стовпці часу (`time_*`, `train_ms`). Щоб повернути закомічені таблиці: `git checkout -- results/`.

## Результати

> Усі числа нижче отримано на **синтетичних даних** (`SyntheticLog`, D-008) і з коефіцієнтами
> Q за замовчуванням (α = 0.5, β = 0.3, γ = 0.2, D-007), бо матеріалів викладача в репозиторії ще немає.
> Повні таблиці — у [`results/`](results/).

**Фінальний запуск** ([results/final.md](results/final.md)), сесія 2000 подій, параметри від ГА:

| Сценарій | S | R | T | Q | Відкинуто пакетів |
|---|---|---|---|---|---|
| none | 1.0000 | 1.0000 | 0.2125 | 0.8425 | 0 |
| node-loss | 1.0000 | 1.0000 | 0.2125 | 0.8425 | 0 |
| two-node-loss | 1.0000 | 0.7870 | 0.2125 | 0.7786 | 0 |
| corrupt | 1.0000 | 1.0000 | 0.2125 | 0.8425 | 2 |
| mixed | 1.0000 | 1.0000 | 0.2125 | 0.8425 | 1 |
| **середнє** | **1.0000** | **0.9574** | **0.2125** | **0.8297** | |

Стиснення Гаффманом: 32 000 → 22 428 байтів (−30%). Пошкоджені пакети в усіх сценаріях
відкинуто за HMAC; сторонніх записів у відновленому журналі — 0.

**ДП проти жадібного** ([results/dp_vs_greedy.md](results/dp_vs_greedy.md)): на задачах із сесії
(n = 100…2000) обидва алгоритми дали однакову корисність, але ДП у 10–25 разів повільніший
(до ~0.5 с на 2000 подій). На 2000 випадкових малих задачах жадібний гірший за ДП у 49.9% випадків
(у найгіршому — 0.46 від оптимуму), ДП не гірший ніколи.

**Класифікатор** ([results/classifier.md](results/classifier.md)) на valid (1500 подій):

| Модель | Accuracy | Macro-F1 | F1 класу 0 / 1 / 2 |
|---|---|---|---|
| Перцептрон (16 ознак → 16 → 3) | 0.8627 | 0.7675 | 0.912 / 0.633 / 0.757 |
| Правило за severity/critical | 0.8780 | 0.7279 | 0.946 / 0.521 / 0.717 |

**ГА проти випадкового пошуку** ([results/ga_convergence.md](results/ga_convergence.md)), функція
Растригіна, 10 генів, однакова кількість обчислень fitness (2320), середнє за 5 seed:
ГА −3.98, випадковий пошук −84.01 (оптимум 0).

**Підбір параметрів ГА** ([results/ga_tuning.md](results/ga_tuning.md)): на 300 подіях і трьох
сценаріях Q виріс з 0.7780 (параметри за замовчуванням) до 0.8010; випадковий пошук з тим самим
бюджетом (92 обчислення) дав 0.8011, тобто на цій задачі ГА переваги не має (див. «Відомі обмеження»).

**Абляція** ([results/ablation.md](results/ablation.md)), середнє за 5 сценаріями:

| Конфігурація | S | R | T | Q |
|---|---|---|---|---|
| повна система (MLP + ДП + ГА) | 1.0000 | 0.9574 | 0.2125 | 0.8297 |
| без перцептрона | 1.0000 | 0.9574 | 0.2125 | 0.8297 |
| без ДП (жадібний) | 1.0000 | 0.9574 | 0.2125 | 0.8297 |
| без ГА (параметри за замовчуванням) | 1.0000 | 0.8058 | 0.5229 | **0.8463** |

Результат детермінований: seed генераторів даних, ініціалізації перцептрона і ГА зафіксовано.
Випадковими є лише сіль і nonce кожного пакета LOG3 — вони не впливають на S, R, T, Q.
Після того як у `materials/` з'являться файли викладача, ті самі команди автоматично
візьмуть їх замість синтетики (джерело друкується в App і записується під кожною таблицею).

## Відомі обмеження

- **Немає матеріалів викладача.** `replication.py`, `REPLICATION_SPEC.md`, `FORMAT_SPEC_P3.md`,
  `team_config.json`, CSV і `session.bin` ще не отримано. Тому всі результати — на синтетиці,
  коефіцієнти Q — значення за замовчуванням, вузли — у пам'яті, формат запису не звірено з `session.bin` (D-003).
- **replication.py не перевірено.** `ReplicationBridge` і `PythonReplicaStore` протестовано на тестових
  Python-скриптах; точні аргументи `replication.py` треба задати через `--replication-args` після
  читання специфікації. Якщо формат обміну інший — потрібна ще одна реалізація `IReplicaStore` (D-005).
- **Визначення S, R, T — наші** (D-007), до звірки з `team_config.json`.
- **Параметри від ГА гірші на повній сесії.** ГА налаштовував параметри на 300 подіях і трьох
  сценаріях з відмовами; на 2000 подіях і всіх п'яти сценаріях вони дають Q = 0.8297 проти 0.8463
  за замовчуванням: ГА обрав бюджет 2.49 копії, що підняло R, але знизило T. Це перенавчання на
  налаштувальній вибірці — підбір треба робити на тих самих даних і сценаріях, що й оцінку.
- **ГА не кращий за випадковий пошук у підборі параметрів** (0.8010 проти 0.8011): 5 генів,
  92 обчислення і плоский ландшафт Q, де основний вплив має лише `BudgetFactor`.
  Перевага ГА чітко видна лише на 10-вимірній тестовій функції.
- **Абляція з параметрами ГА неінформативна для перцептрона й ДП.** При бюджеті 2.49 копії кожна
  подія отримує 2–3 копії, тож вибір класу і алгоритму не змінює S, R, T, Q (різниця видна лише в
  `plan_utility`). S = 1 у всіх конфігураціях, бо критичні події завжди отримують 3 копії.
- **ДП і жадібний збігаються на реальній формі задачі.** Корисність u_i(r) = v_i·(1 − p^r) угнута,
  а ваги малі відносно бюджету — за таких умов жадібний майже оптимальний; перевага ДП видна лише
  на випадкових задачах.
- **Продуктивність.** PBKDF2 (100 000 ітерацій) рахується для кожного пакета окремо (своя сіль),
  тому наскрізний запуск триває десятки секунд. Таблиця ДП обмежена 40 млн клітинок: для більших
  сесій ваги й бюджет масштабуються, що трохи огрублює розв'язок.
- **Класифікатор** слабко розрізняє клас 1 (F1 = 0.63) — аномалії плутаються зі штатними подіями.

## Правила роботи з Git

1. Усі задачі — через **issue** (одна issue = одна невелика задача з чітким результатом).
2. Для кожної issue — окрема гілка `feature/<модуль>-<суть>`. **У `main` напряму не комітимо.**
3. У кожному коміті — номер issue та зрозумілий опис: `add canonical Huffman encoder (#14)`. Не `fix`, `new`, `final`.
4. Перед PR запускаємо `dotnet test` — усе має проходити.
5. Pull request у `main` переглядає інший учасник (review за колом). `main` завжди проходить тести.
6. Щонайменше один змістовний коміт на тиждень від кожного.
7. Технічні рішення записуємо в `docs/decisions.md`.
